```bash

```

Documentos, todos en esa rama:

- `docs/superpowers/specs/2026-08-12-test-strategy-design.md` — el spec. **Es la autoridad**:
  ante una contradicción entre un plan y el spec, gana el spec.
- `docs/superpowers/plans/2026-08-13-coverage-infra-and-phase1.md` — plan de Fase 0 + 1
- `docs/superpowers/plans/2026-08-14-phase2a-auth-cart.md` — plan de Fase 2a

Para escribir la Fase 2b **no hace falta otro brainstorming**: el spec ya decidió targets,
convenciones, exclusiones y orden. Lo que falta es un plan, no un diseño.

**Nota sobre el tamaño de los planes**: la Fase 2 se partió en tres (2a/2b/2c) a propósito.
Un solo plan para los 7 feature packages serían ~8.000 líneas y en su mayoría adivinadas,
porque el plan lleva el código de test real y eso exige leer cada package antes de escribirlo.

## 5. Lo único que no puede hacer nadie más que el equipo

**Agregar "Coverage gate" como required check en branch protection de `develop`.**

Hasta que eso pase, todo el gate es informativo: se puede mergear un PR que baje `auth` de
97.8% a 5% y CI lo reporta en verde y lo deja pasar. Es un cambio de configuración del repo,
no de código, y no está en ningún diff.

## 7. Bugs reales que encontraron los tests

Ninguno se conocía antes.

1. **`DateTimeUtils.isDayPartiallyFull`** tenía `start.isBefore(x) && start.isAfter(x)` —
   insatisfacible, código muerto— más un error de precedencia (`&&` liga más fuerte que `||`),
   así que el guard `!fullDayOverlap` colgaba solo de la tercera cláusula. Arreglado en #170.
2. **`LocalAuthRepository.refresh()`** dejaba escapar excepciones del `try/catch`. Es el mismo
   defecto que arregla #172, encontrado desde la dirección opuesta: #172 salió de un warning
   del analizador, este de un test de runtime.
3. **`MockLocalAuthRepository.refresh()`** casteaba `http.Response.body` (un `String`) directo
   a `Map`: siempre tiraba, siempre deslogueaba. Arreglado en #175.

Y cinco fallas silenciosas del propio CI, todas de la misma clase:

- el script `test` de melos devolvía éxito para packages sin tests
- `test:coverage` sin `set -e` se tragaba fallas reales de test
- un `coverage_thresholds.yaml` vacío reportaba éxito sobre cero packages
- `--update` sin reportes ponía todos los floors en 0 y salía 0
- **los 23 tests del propio gate nunca corrían en CI** (el package raíz no está en el
  workspace de melos y CI solo invocaba `melos ...`)
